<p>A while ago I was reviewing some code and I came across some code that looked like this</p><pre>if (corpus.Where(a =&gt; a.SomeProperty == someValue).Count() &gt; 0)
{
    // Do Stuff
}</pre>
<p>And it got me thinking that it may not be the best way to do this. What is really being asked here is: “Are there any items in the enumerable?” The count is not actually important in this situation. I considered that it would probably be more efficient to write:</p><pre>if (corpus.Where(a =&gt; a.SomeProperty == someValue).Any())
{
    // Do stuff
}</pre>
<p>Then I read somewhere (unfortunately, I didn’t note the URL) that for certain situations the <code>.Any()</code> extension method on <code>IEnumerable&lt;T&gt;</code> can be inefficient in certain scenarios. For instance, if concrete type is actually a <code>List&lt;T&gt;</code> which maintains its own <code>Count</code>. In that instance the cost of setting up the <code>Enumerator</code> and calling <code>MoveNext()</code> to determine the existence of at least one element would be more expensive an operation than calling <code>Count</code> on the <code>List&lt;T&gt;</code>.</p>
<p>I was curious about that so I set about working out the relative performance characteristics of a number of the LINQ extension methods. I should note that these were all on LINQ to Objects out of the box so don’t measure how these methods would perform relatively for things like, say, LINQ to SQL.</p>
<p>I tested various scenarios, some where the <code>IEnumerable&lt;T&gt;</code> is a lightweight generator of elements, in this case an <code>Enumerable.Range(…)</code>, in other cases I used a <code>List&lt;T&gt;</code> either by a concrete reference or by an reference to the <code>IEnumerable&lt;T&gt;</code> interface.</p>
<p>All timings in this post relate to my desktop machine which is running Windows 7 64bit with 8Gb RAM and an AMD Phenom II X4 955 running at 1.6GHz (which for some unknown reason it won’t run at the full 3.2GHz)</p>
<h3>Counting elements</h3>
<p>In the first set of tests I counted the number of elements. For the cases where I called the <code>Count</code> property directly on the <code>List&lt;T&gt;</code> and used the <code>Count()</code> extension method on <code>IEnumerable&lt;T&gt;</code> where the concrete type was the <code>List&lt;T&gt;</code> the result was returned in O(1). The LINQ method was 24 times slower.</p>
<p>Where the <code>IEnumerable&lt;T&gt;</code> did not also implement the <code>ICollection&lt;T&gt;</code> interface (as in the case where the values were being generated by <code>Enumerable.Range(…)</code> method) the <code>Count()</code> extension method took O(n) time to return the answer.</p>
<p><img style="display:block;float:none;margin-left:auto;margin-right:auto;" src="http://static.colinmackay.co.uk/images/performance/2011-08-13-ienumerable-count.png"></p>
<p>The graph above shows the number of Ticks (vertical axis) taken to complete the counting task with n (horizontal axis) elements. A tick is roughly 1/1600<sup>th</sup> of a millisecond. So for 2000000 elements it took 72.5ms to count them.</p>
<p>Compare that for instances where the <code>Count</code> property was called directly (0.00413 Ticks or 0.00258µs [millionths of a second]) or where the <code>Count()</code> method was called on something that could be cast to an <code>ICollection</code> or <code>ICollection&lt;T&gt;</code> (0.0989 Ticks or 0.0618µs)</p>
<p>So far it looks good for cases where the underlying type implements the <code>ICollection&lt;T&gt;</code> or <code>ICollection</code> interface. However remember as soon as you start filtering the data (e.g. with a <code>Where()</code> method call) then you are returning an <code>IEnumerable&lt;T&gt;</code> which then operates in O(n) time. Also remember that the <code>Where()</code> clause will add some overhead as it has to process the filter as well.</p>
<h3>Any elements</h3>
<p>It should be no surprise that using our test set of a <code>List&lt;T&gt;</code> and an <code>Enumerable.Range(…)</code> the <code>Any()</code> method runs in O(1) time. Both took similar amounts of time, the former taking 0.278 Ticks (0.174µs) per call, and the latter taking 0.296 Ticks (0.185µs) per call. I suspect that time on the latter is more due to the the small amount of additional time taken to generate additional elements as the enumerator progresses.</p>
<p>However, if you have a reference to something that already implements <code>ICollection&lt;T&gt;</code> which defines a <code>Count</code> property, such as a <code>List&lt;T&gt;</code>, you may find it is faster to perform <code>(corpus.Count&gt;0)</code>. I found that for the <code>List&lt;T&gt;</code> I’d created for the test runs it was only marginally slower than the raw call to <code>Count</code> taking 0.00607 ticks (0.00379µs) per call.</p>
<h3>Any elements with filter</h3>
<p>If you have a filter (a Where clause) then Any may take longer that O(1). It will take as long as it takes to find anything that matches the filter or O(n) if nothing matches the filter.</p>
<p>I ran three tests, one where the filtered condition was met on the first element, one where the condition was met in the middle of the set and one where the condition was not met until the last element.</p>
<p><img style="display:block;float:none;margin-left:auto;margin-right:auto;" src="http://static.colinmackay.co.uk/images/performance/2011-08-13-filtered-any.png"></p>
<h3>Summary</h3>
<p>If you have a concrete type the performance is better when using the <code>Count</code> property both for cases when you need to know the number of elements in the corpus or when you need to know if there any any elements at all.</p>
<p>If you simply need to know if there are any elements at all in the corpus then the use of <code>Any()</code> works out better than using the LINQ extension method <code>Count()</code> as <code>Count()</code> must traverse the entire corpus (unless it derives from <code>ICollection&lt;T&gt;</code> whereas <code>Any()</code> will short circuit at the first available opportunity.</p>
