Way back in 2004, I wrote a blog post about a lazy `NotSupportedException` method that used reflection to work out where wasn't supported so you didn't get a generic method in your logs.

Looking back, it was a naïve implementation.
* It should have thrown a `NotImplementedException`.
* It was a method on a base class which meant it wasn't very portable.
* The message produced (e.g. "The Method OverrideMe is not supported by ConsoleApp4.MyDerivedClass") pointed at the derived class, which didn't impelement the method, so if you went looking you'd potentially have a frustrating time tracking down a method that only existed on the base class.
* Since then, .NET has come along and the compiler can work some of this out for itself at compile time.

I've now reworked it so that it is in a helper class instead and therefore available whereever you need it to be. I've also made the message a bit clearer as to what the potential issue is.

## The code

There are two public methods on the helper class. `NotImplementedException` which just builds the exception object so you can throw it yourself, and `ThrowNotImplementedException` which will build and throw the exception for you.

```csharp
public static class ExceptionHelper
{
    public static NotImplementedException NotImplementedException(object obj,
        [CallerMemberName] string? memberName = null)
    {
        return BuildNotImplementedException(obj, 3, memberName);
    }

    [DoesNotReturn]
    public static void ThrowNotImplementedException(object obj,
        [CallerMemberName] string? memberName = null)
    {
        throw BuildNotImplementedException(obj, 3, memberName);
    }

    private static NotImplementedException BuildNotImplementedException(object obj, int skipFrames,
        string? memberName)
    {
        var type = obj.GetType();
        var qualifiedTypeName = type.FullName;
        var message = $"{qualifiedTypeName}.{memberName} is not implemented.";

        if (IsUnimplementedVirtualMember(obj, skipFrames: skipFrames, out Type? declaringType, out bool noOverrideType))
        {
            if (noOverrideType)
            {
                message += $" (likely cause: '{memberName}' is virtual on '{declaringType!.FullName}' and this is not a derived type that overrides it.)";
            }
            else
            {
                message += $" (likely cause: '{memberName}' is virtual on '{declaringType!.FullName}' and '{qualifiedTypeName}' does not override it.)";
            }
        }

        return new NotImplementedException(message);
    }

    private static bool IsUnimplementedVirtualMember(object obj, int skipFrames,
        out Type? declaringType, out bool noOverrideType)
    {
        declaringType = null;
        noOverrideType = false;

        var callingMethod = new StackFrame(skipFrames, false).GetMethod() as MethodInfo;
        if (callingMethod is null || !callingMethod.IsVirtual)
        {
            // It's not a method or it's not a virtual method.
            // This will pick up property getters and setters.
            return false;
        }

        declaringType = callingMethod.DeclaringType;
        if (declaringType is null)
        {
            return false;
        }

        var runtimeType = obj.GetType();
        if (runtimeType == declaringType)
        {
            // obj is literally an instance of the declaring type - there is no derived class
            // that could have overridden it.
            noOverrideType = true;
            return true;
        }

        var parameterTypes = callingMethod.GetParameters().Select(p => p.ParameterType).ToArray();
        var resolvedMethod = runtimeType.GetMethod(
            callingMethod.Name,
            BindingFlags.Instance | BindingFlags.Public | BindingFlags.NonPublic,
            binder: null,
            types: parameterTypes,
            modifiers: null);

        // If we can't resolve a matching method (e.g. explicit interface implementations),
        // assume the worst - it isn't overridden.
        if (resolvedMethod is null)
        {
            return true;
        }

        // resolvedMethod is the most-derived override reachable via virtual dispatch on
        // runtimeType. If it's still declared on the same type as the currently executing
        // method, nothing in between overrode it.
        return resolvedMethod.DeclaringType == declaringType;
    }
}
```

## Example usage

Set up the base and derived classes. The base has a virtual method that does not contain an implementation. and the derived class does not override it.
```csharp
public class MyBaseClass
{
    public virtual void OverrideMe()
    {
        ExceptionHelper.ThrowNotImplementedException(this);
    }
}

public class MyDerivedClass : MyBaseClass
{
}
```

# NOTES
In C# are there scenarios where I might want to create a base class with a virtual method without an implementation that just throws a NotImplementedException instead of declaring the base class and method as abstract and having the compiler throw an error at any lack of implementation?

Yes, several legitimate scenarios:

1. Binary/source compatibility in public libraries
If your base class ships in a NuGet package or is used by third parties, adding a new abstract member breaks every existing subclass — they won't compile until they implement it. A virtual method with a NotImplementedException (or better, NotSupportedException) lets you extend the base class without breaking consumers who haven't opted in yet.

2. The base class must be instantiable itself
abstract classes can't be instantiated directly. If you sometimes need a plain, usable instance of the base class (e.g., as a default/no-op case, or because generic code does new T()), it can't be abstract — so unimplemented behavior has to be virtual-and-throw instead.

3. Optional capabilities, not universal ones
Template Method / plugin-style designs often have many hook methods where each derived class only needs to override a handful. Making them all abstract forces every subclass to write empty/boilerplate overrides for methods that don't apply to it. Classic real-world example: System.Configuration.Provider.ProviderBase-style APIs and old ADO.NET provider classes, where most concrete providers only implement a subset of virtual members and the rest throw NotSupportedException.

4. Interface Segregation violations you can't fix
When implementing a wide interface (often one you don't control) via an abstract base, some members genuinely don't apply to certain subclasses. Throwing communicates "this operation is not supported for this implementation" — a NotSupportedException is often more semantically correct than NotImplementedException here (see Stream.Write throwing when CanWrite is false).

5. Staged/incremental development
During active development, you might scaffold a base class with throwing virtuals as placeholders, intending to make it abstract later once the API stabilizes — though this is more a workflow convenience than a permanent design choice.

A couple of caveats worth noting:

If every concrete subclass truly must implement the method, abstract is almost always better — compile-time safety beats a runtime surprise.
If you go the throwing-virtual route, prefer NotSupportedException over NotImplementedException when the meaning is "this operation isn't valid here" rather than "this hasn't been written yet" — NotImplementedException in shipped code reads as a TODO left in by mistake.
Consider whether an interface with default interface methods (C# 8+) or composition (strategy objects instead of subclassing) sidesteps the problem entirely — sometimes the throwing-virtual pattern is really a symptom of forcing too much into one hierarchy.
